    DI10 E-Stop & KM1 Hardwired Relay Two-State Verification

    VERIFYING
    DI10 Physical Value -- High (1) when released, Low (0) when pressed
    Logical E-Stop State -- Must be CLEAR before motion can arm
    Polarity Commissioning -- NC contact verified via two-state test
    KM1 Safety Relay Contact HARDWIRED 60V X/Y cut; 24V Z inspection gate
    Two-State Commissioning Procedure:
    1. Release physical E-Stop button at the cabinet: verify raw DI10 reads 1 (High) and logical E-Stop is CLEAR.
    2. Press physical E-Stop button: verify raw DI10 toggles to 0 (Low) and state transitions immediately to E_STOP.
    3. If the raw bit does not toggle, inspect cabinet wiring and KM1 safety relay contacts. Never compensate in software without two confirmed states.

    Hardware Safety Interlock Gate

    DI10 E-Stop Contact & KM1 Power Relay Diagnostic

    VERIFYING
    DI10 Physical Bit -- High (1) = Released / Closed Loop, Low (0) = Pressed / Open
    Logical E-Stop State -- Must be CLEAR before motion can arm
    Contact Polarity -- NC contact verified via two-state operator test
    KM1 Contactor Relay -- Main 60V power circuit contactor
    On-Site Check Procedure:
    1. Ready state: Release the E-Stop, verify the NC contact is closed, 24 V reaches DI10, raw DI10 reads 1 (High), and Logical E-Stop is CLEAR.
    2. Tripped state: Press the E-Stop and verify the circuit opens, raw DI10 changes to 0 (Low), KM1 removes motor power, and the machine immediately enters ALARM / E_STOP.
    3. Limit test: Manually actuate each axis limit switch and verify that the matching DI0–DI5 card changes to TRIGGERED.

    System Design Reference

    NARIT Vending Architecture

    2 PROCESS / 1 MQTT CLIENT

    Responsibilities are strictly separated: the Web HMI presents state and sends requests, the Controller owns safety decisions and GPIO control, and a single MQTT client runs inside the Controller to prevent duplicate client IDs and connection instability.

    01

    Operator HMI

    The operator browser provides Dashboard, Motion, Slots, Alarms, and MQTT Monitor workspaces.

    HTTP polling: GET /api/state every 1.5 seconds
    HTTP / JSON→
    02

    Web Process

    Flask on port 80 serves HTML/CSS/JavaScript and API requests only. It never opens GPIO or creates an MQTT client.

    Controller unavailable → command API returns 503
    Unix IPC→
    03

    Controller Process

    Owns machine state, the command bus, interlocks, MotionService, GPIO, and the single MQTT client.

    /run/narit-vending/ctrl.sock
    GPIO↘
    MQTT↗
    04

    Machine / Broker

    Drives X/Y/Z Step, Direction, and Enable signals; reads limits and E-Stop; and exchanges commands with the MQTT broker.

    Hardware safety remains local

    A. Web HMI

    Presentation & Request Layer

    • HTML/CSS/JavaScript displays XYZ position, homing state, alarms, slots, and Controller logs.
    • Home, Jog, GO TO SLOT, Dispense, and Reset Alarm use the REST API; the page never controls motors directly.
    • The Web process uses ControllerClient over IPC, isolating web crashes or restarts from machine motion.
    • MQTT Monitor reads telemetry through IPC, so the Web process never creates a duplicate MQTT client.

    B. Controller

    Safety & Motion Authority

    • Starts MotionService, then creates the StateMachine, CommandBus, and IPC Server before accepting commands.
    • Command handlers cover Stop, Clear Alarm, Home, Jog, Move, Go To Slot, Dispense, Validate/Arm, and Motor Test.
    • Every command checks interlocks before GPIO output: Controller online, E-Stop clear, software stop clear, no blocking alarms, homing complete, and coordinates within limits.
    • Targeted moves follow Validate → Arm → Execute so changed coordinates or speed cannot run without a fresh validation.

    C. Hardware Safety

    Local, Immediate Interlocks

    • GPIO drives Step, Direction, and Enable for X, Y, and Z; only MotionService can access these devices.
    • Minimum/maximum limit switches and the physical E-Stop stop or reject unsafe movement.
    • Homing establishes a reference before absolute moves or slot positioning; a restart requires homing to be verified again.
    • GO TO SLOT uses Safe Z before X/Y motion, and Dispense is allowed only at the verified slot position.

    D. MQTT Contract

    Controller-owned Persistent Session

    • The Controller owns one connection with a cabinet-specific client ID and clean session = false; the Web process never connects to the broker.
    • Subscribe: cabinet/{cabinet_id}/command; the supported action is release and requires request_id and slot.
    • Publish: /scan, /status, and /presence; presence uses QoS 1, retained delivery, and an offline Last Will.
    • Network or broker failures reconnect with a 4–60 second backoff; telemetry reports connection counts and the latest error.

    E. Configuration & Audit

    Validated Machine Definition

    • machine_config.json stores travel, steps/mm, Safe Z, home sequence, and slot XYZ; hardware_config.json stores GPIO and communication settings.
    • Before saving configuration, the system validates it, creates a revision, and stores a backup under backups/config/.
    • Event logs, machine snapshots, and MQTT telemetry support fault analysis without exposing passwords or tokens.

    F. Deployment Rule

    Keep MQTT Online During UI Work

    • Web-only deployment copies only static/ and templates/, then restarts only the Web process.
    • The Controller and MQTT connection therefore remain online during UI work.
    • Use full deployment for Controller, GPIO, motion, or MQTT changes; restarting the Controller briefly publishes the actual offline presence state.

    Command Path

    Example: Dispense Command from Backend

    1. The backend publishes release to cabinet/{cabinet_id}/command with request ID, slot, and optional expiry time.
    2. MQTTService validates JSON, action, request ID, slot, and expiry, and prevents duplicate request IDs from running twice.
    3. The Controller checks safety interlocks, homing, slot XYZ, and the Safe Z → X/Y → target Z sequence before motion.
    4. Results are published as received / phase / success or failed, with the reason and target/home verification.
    5. The HMI reads state through Web → IPC and displays the same state used by the Controller; neither browser nor MQTT paths can bypass the safety layer.
