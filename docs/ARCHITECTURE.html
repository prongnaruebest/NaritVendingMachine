Current Production Architecture (v3)

This is the authoritative description of the running cabinet architecture. It supersedes older single-process descriptions elsewhere in this document. Web presentation and machine control are deliberately separate processes.

Safety boundary: only the Controller process can access MotionService, GPIO, safety interlocks, or the cabinet MQTT client. Browser and Web process requests must cross IPC; they cannot bypass Controller validation.
Operator BrowserHTTP/JSONWeb Process (Flask :80)Unix IPCController ProcessGPIOX/Y/Z + SensorsMQTTBroker

Web HMI and Web Process

Flask serves HTML, CSS, JavaScript and HMI APIs on port 80. It uses ControllerClient over /run/narit-vending/ctrl.sock. It never opens GPIO and never creates an MQTT client. If IPC is unavailable, commands fail safely with HTTP 503. A web-only deployment restarts only Web, preserving machine control and MQTT.

Controller Process

The Controller is the sole motion authority. It creates MotionService, SequenceService, StateMachine, CommandBus, handlers and IPC server, and produces the snapshot used by HMI/MQTT. It owns Stop, Clear Alarm, Home, Jog, Move, Slot, Dispense, validation/arm, Motor Test and RUN_SLOT_SEQUENCE handlers.

Slot Sequence Ownership

controller/sequence_service.py owns: validate → Move X → Move Y → Move Z → verify target → hold 3 seconds → Home Z → Home Y → Home X → verify home. It orchestrates only; motion.py remains the GPIO owner and checks E-Stop, stop latch, limits and travel during each physical move.

Safety and Motion

Every motion request is rechecked by Controller: physical E-Stop, software stop, active fault alarms, limit switches, homing, configured travel and target validity. Target motion follows Validate → Arm → Execute. Standard Go To Slot uses Safe Z before X/Y travel; the separately selected Slot Sequence follows its defined X → Y → Z → hold → Home Z/Y/X workflow.

MQTT Ownership

Controller owns exactly one cabinet-specific MQTT client with clean_session=false. Web reads sanitized MQTT telemetry through IPC. Presence is retained QoS 1 with Last-Will offline; reconnect backoff is 4–60 seconds. This prevents duplicate client IDs and connection flapping.

Actual Sequence Module Boundary

HTTP / HMI

web/routes/commands.py accepts the sequence endpoint and forwards a RUN_SLOT_SEQUENCE envelope over Unix IPC. Browser JavaScript only selects standard Go To or Sequence Mode; it never contains motor logic.

MQTT

mqtt_service.py validates release, expiry and idempotency, then creates one in-memory RUN_SLOT_SEQUENCE CommandEnvelope with source mqtt. The original request ID is the idempotency key and every final MQTT status is sanitized.

CommandBus / Handler

controller/__main__.py binds MQTT to CommandBus.submit. handlers/sequence.py is called only after SafetyInterlock accepts the command and delegates to service.sequence_service.

Sequence / Motion

SequenceService publishes phases and aborts on a failed stage. It does not write GPIO. motion.py remains the hardware boundary: AxisController owns pulses, position, limits, E-Stop and stop checks.

HMI Command Flow

Browser loads index.html and app.js from Web. A route in web/routes uses ipc_client.py to send a CommandEnvelope to controller/server.py. CommandBus invokes SafetyInterlock; only then can handlers call motion.py and GPIO. Snapshot returns through IPC to Web and Browser.

MQTT Command Flow

controller/__main__.py starts mqtt_service.py; Web never owns MQTT. MQTT validates release/request_id/slot/expiry/idempotency, creates one RUN_SLOT_SEQUENCE command, and publishes presence, phases and final status. Web MQTT Monitor reads sanitized telemetry through IPC.

Pi Process Ownership

narit-vending-controller.service owns GPIO, Controller and MQTT. narit-vending-web.service serves port 80 and depends on Controller IPC. Web-only deployment restarts only Web; full deployment restarts Controller and presence is offline during the true restart window.

Safety Rule

HMI and MQTT cannot bypass Controller. E-Stop, stop latch, active alarm, busy state, homing, limits, travel and target/slot validity are checked before GPIO. Standard Go To Slot uses Validate → Arm → Execute and Safe Z; the selected sequence is an independently defined controller workflow.

Presentation: What This Architecture Proves

One Safety Authority

HMI and MQTT are different inputs, not different control paths. Both converge at Controller CommandBus and SafetyInterlock; neither Web nor MQTT can access GPIO directly.

Deterministic Commands

CommandBus serializes motion with a single-flight dispatch. MQTT preserves request_id as its idempotency key and rejects expired or duplicate release messages.

Safety Is Continuous

Interlocks decide whether a command may start. During each physical move, AxisController still checks E-Stop, stop latch, limits and travel. The 3-second sequence hold also polls stop/E-Stop.

Independent Deployment

Web-only deployment refreshes HMI assets without restarting Controller or the cabinet MQTT client. A full deployment is used only when the Controller runtime changes.

Configuration and Audit

machine_config.json defines travel, steps/mm, Safe Z, homing and slot XYZ. hardware_config.json defines GPIO and communication. Valid saves are revisioned and backed up under backups/config/.

Operational Checks

/health/live checks Web availability. /health/ready separates service readiness from machine readiness. /api/mqtt/status returns sanitized telemetry only. A machine may be service-ready but not ready for motion until homed and clear.

Deployment Rule

Use Web-only deployment for HMI assets. Use full deployment only for Controller, motion, GPIO, MQTT runtime or dependencies; Controller restart truthfully publishes offline during its restart window.

Failure Behavior

Web failure does not grant motor access. Controller failure makes commands unavailable. MQTT loss does not bypass local safety or stop local HMI control. Physical E-Stop is local and immediate.

Detailed Production System Flow

This flow describes what the running system does for every HMI or MQTT motion request. The Controller is the only component allowed to make a safety decision or access GPIO.

Input and validation

HMI requests arrive through Web/IPC. MQTT accepts only release with request ID and slot. Invalid, expired or duplicate MQTT requests are rejected before motion.

Safety decision

SafetyInterlock checks E-Stop first, then stop latch, alarm, busy state, motor test, homing, limit conflict and target validity. A rejected command returns a reason and never reaches GPIO.

Motion sequence

Handlers call MotionService only after approval. Slot travel raises Safe Z before X/Y movement, approaches target Z, verifies the position and permits dispense only at the verified slot.

Result and visibility

Controller returns a MachineSnapshot through IPC for HMI. MQTT publishes sanitized lifecycle/result telemetry. Both views reflect Controller state, not independent browser state.

Detailed Axis Homing Flow

Homing establishes the physical reference used by absolute motion. The Controller executes the configured sequence (normally Z → Y → X) and rechecks safety continuously; an axis is not marked homed until its reference procedure completes.

flowchart LR A["1. HOME request\naxis or all"] --> B{"2. Controller safety check\nE-Stop · alarm · stop latch · busy"} B -->|"blocked"| X["Reject\nshow corrective reason"] B -->|"allowed"| C["3. Build configured sequence\nZ → Y → X for HOME ALL"] C --> D["4. Select next axis\nclear previous homed flag"] D --> E["5. Search toward home reference\nGPIO pulse + sensor polling"] E --> F{"6. Home switch reached?"} F -->|"no"| G{"timeout / limit conflict / stop?"} G -->|"continue"| E G -->|"fault"| H["Fail homing\nstop axis, record reason, no homed state"] F -->|"yes"| I["7. Backoff / settle\nset reference position"] I --> J["8. Mark axis homed\nupdate MachineSnapshot"] J --> K{"more axes in sequence?"} K -->|"yes"| D K -->|"no"| L["9. HOME complete\nabsolute motion may be permitted"]

Before Home

Home is rejected when E-Stop, blocking alarm, stop latch or an active motion command makes it unsafe. Controller reports the specific reason; HMI cannot force the axis to move.

Reference search

Each axis moves toward its configured home direction while Controller monitors the home/limit input, timeout and stop state. Unexpected sensor conflict or timeout stops the axis and leaves it not homed.

Reference confirmation

After the home switch is detected, the controller performs configured backoff/settling and sets the axis reference position. Only a completed procedure marks that axis homed.

After Home

HOME ALL proceeds to the next configured axis. Absolute move, Go To Slot and Dispense remain blocked until all required axes are homed and all other safety interlocks are clear.

Detailed Go To Slot Flow

Go To Slot is a controlled positioning workflow. A selected slot is not enough: Controller must verify safety, homing and valid saved XYZ before any axis is moved.

flowchart LR A["1. Select slot\nload saved X/Y/Z"] --> B{"2. Slot valid?\nall XYZ finite and within travel"} B -->|"no"| X["Reject\ncorrect slot configuration"] B -->|"yes"| C{"3. Motion allowed?\nE-Stop · stop · alarm · busy · homing"} C -->|"no"| Y["Blocked\nshow interlock reason"] C -->|"yes"| D["4. Confirm target\nslot, XYZ, speed and safe area"] D --> E["5. Raise Z to Safe Z\nclear product before X/Y travel"] E --> F{"Safe Z reached?"} F -->|"no / fault"| Z["Stop and fail\nrecord verification reason"] F -->|"yes"| G["6. Move X/Y\ncontrolled trajectory to slot row/column"] G --> H{"X/Y target reached?"} H -->|"no / fault"| Z H -->|"yes"| I["7. Move Z to saved target depth"] I --> J{"8. Verify final XYZ\nwithin positioning tolerance"} J -->|"no"| Z J -->|"yes"| K["9. Publish success\nslot is eligible for Dispense"]

Slot validation

Controller requires a configured slot with valid finite X/Y/Z coordinates inside machine travel. Empty, unconfigured or invalid slots cannot start motion.

Safety before travel

Controller checks E-Stop, stop latch, active alarm, busy state and homing before Go To Slot. The HMI confirmation is informational; it does not bypass safety.

Safe movement order

Z is raised to configured Safe Z first, then X/Y move to the slot, then Z approaches the saved depth. A fault or failed target verification stops the workflow and returns a reason.

Dispense boundary

Go To Slot only positions the gantry. Dispense is a separate action and may be enabled only after the final position is verified within tolerance and all safety interlocks remain clear.

สั่งจาก Visualizationเลือกช่อง 1–30 ในตาราง 6×5 ช่องที่บันทึกแล้วจะสั่ง Go To Slot ทันที ส่วนช่องว่างถูกปิดใช้งาน
